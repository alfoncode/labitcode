Si has intentado interactuar con modelos de lenguaje y has sentido que las respuestas son inconsistentes, no estás solo. Escribir buenos prompts no es una cuestión de "magia" o intuición; es una disciplina de ingeniería con patrones claros y deterministas.

Recientemente, el canal de **Manu Acevedo** analizó en profundidad el taller oficial de **Anthropic** sobre ingeniería de prompts ([ver video en YouTube](https://www.youtube.com/watch?v=kcKMyObtrxY)), destacándolo como un recurso gratuito que supera con creces a cursos de cientos de dólares. El taller original está basado en un [repositorio interactivo de Jupyter Notebooks de Anthropic](https://github.com/anthropics/prompt-eng-interactive-tutorial) y detalla exactamente cómo "piensa" y procesa la información su modelo estrella, **Claude**.

En esta guía, destilamos las lecciones clave del taller oficial con ejemplos reales de código, patrones de diseño de prompts y explicaciones técnicas de por qué funcionan estas técnicas.

## El Enfoque Mental: Claude como una Herramienta de Poder

Antes de escribir tu primer prompt, es vital cambiar la perspectiva. En el video de Anthropic se enfatiza que Claude no es un buscador web glorificado, sino una **herramienta de poder** (_power tool_). No está diseñado para forzarte a trabajar a su manera, sino para adaptarse a tus propios flujos de trabajo como desarrollador.

Para los ingenieros de software, esto significa tratar los prompts como **código de configuración**. Un buen prompt debe ser estructurado, predecible y fácil de depurar.

## 1. Asignación de Roles (Persona): Definir el Contexto

Uno de los errores más comunes es hacer preguntas directas sin establecer un contexto previo. Claude utiliza la **asignación de roles** (o _personas_) para acotar su espacio de probabilidad semántica, adoptando el tono, las restricciones y el conocimiento específico del rol solicitado.

### ¿Por qué funciona?

Al decirle a Claude que adopte un rol específico, filtras las respuestas irrelevantes y priorizas la terminología y los patrones de pensamiento correctos para esa disciplina.

```markdown
<!-- ❌ Malo: Pregunta directa y genérica -->

Revisa este código y dime si tiene fallos.

<!-- ✅ Bueno: Asignación de rol detallada en la sección System -->

Eres un Ingeniero Principal de Seguridad especializado en Node.js y ciberseguridad web.
Tu tarea es auditar fragmentos de código en busca de vulnerabilidades (como inyección SQL, XSS o fugas de memoria).
Proporciona explicaciones técnicas claras acompañadas de parches correctivos.
```

## 2. La Magia de las Etiquetas XML: El Superpoder de Claude

Si te llevas una sola lección de esta guía, que sea esta: **Claude está preentrenado para reconocer y procesar de forma prioritaria las etiquetas XML** (como `<instrucciones>`, `<contexto>`, `<codigo>`, etc.).

### ¿Por qué son cruciales las etiquetas XML?

1. **Separación Clara de Datos e Instrucciones**: Evita que Claude confunda el contenido que debe _analizar_ con las instrucciones que debe _ejecutar_. Esto previene los ataques de **inyección de prompts** (cuando los datos de entrada contienen instrucciones maliciosas).
2. **Estructura jerárquica**: Permite al modelo navegar por el texto como si fuera un árbol DOM estructurado.
3. **Referencias precisas**: Puedes pedirle a Claude que interactúe directamente con una etiqueta específica (ej. _"Resume únicamente lo que esté dentro de las etiquetas `<documento>`"_).

### Anatomía de un Prompt Estructurado con XML

```xml
Eres un revisor de código automatizado. Tu objetivo es analizar la calidad de una función y sugerir optimizaciones.

<instrucciones>
1. Lee el código fuente proporcionado en la sección <codigo_entrada>.
2. Compara el código con las reglas definidas en <reglas_estilo>.
3. Devuelve los resultados estructurados en un bloque de Markdown.
</instrucciones>

<reglas_estilo>
- Usar TypeScript estricto.
- Evitar bucles anidados si es posible (complejidad O(n^2)).
- Mantener las funciones por debajo de 25 líneas.
</reglas_estilo>

<codigo_entrada>
function processUsers(users: any[]) {
    let result = [];
    for (let i = 0; i < users.length; i++) {
        for (let j = 0; j < users[i].roles.length; j++) {
            if (users[i].roles[j] === 'admin') {
                result.push(users[i]);
            }
        }
    }
    return result;
}
</codigo_entrada>
```

## 3. Few-Shot Prompting: Enseñar con Ejemplos

A menudo, describir un formato de salida complejo con palabras es difícil e impreciso. La mejor forma de guiar a Claude es mediante **Few-Shot Prompting**, es decir, proporcionándole uno o más ejemplos resueltos dentro del propio prompt.

### ¿Por qué funciona?

Los modelos de lenguaje son excelentes imitadores de patrones. Si le muestras exactamente la estructura de entrada y salida que esperas, Claude replicará esa estructura con una precisión del 99%.

```xml
Eres un conversor de lenguaje natural a consultas SQL simplificadas.

<ejemplos>
  <ejemplo>
    <entrada>Dame todos los usuarios registrados en los últimos 30 días</entrada>
    <salida>SELECT * FROM users WHERE created_at >= DATE_SUB(NOW(), INTERVAL 30 DAY);</salida>
  </ejemplo>
  <ejemplo>
    <entrada>Busca el email del usuario con ID 450</entrada>
    <salida>SELECT email FROM users WHERE id = 450 LIMIT 1;</salida>
  </ejemplo>
</ejemplos>

<entrada>
Obtén el total de ventas del producto con ID 10 el mes pasado.
</entrada>
```

## 4. Chain of Thought (Cadena de Pensamiento): Pensar Paso a Paso

Cuando nos enfrentamos a problemas matemáticos o lógicos difíciles, los humanos no respondemos inmediatamente; escribimos pasos intermedios en un papel. Los LLM funcionan igual. Si obligas al modelo a dar una respuesta directa, tiene que adivinar el siguiente token basándose en estadísticas inmediatas, lo que suele llevar a errores.

Si le indicas a Claude que **piense paso a paso antes de responder**, el modelo usará tokens intermedios para calcular la lógica del problema antes de llegar a la conclusión.

### Cómo Implementarlo con XML (`<thinking>`)

Un truco avanzado de desarrollo consiste en pedirle a Claude que escriba su proceso de razonamiento dentro de etiquetas `<thinking>` y su respuesta final en otra sección. De este modo, en tu aplicación puedes extraer únicamente el resultado final mediante expresiones regulares o selectores de etiquetas, ocultando el pensamiento al usuario final.

```xml
Determina si el siguiente número es primo y explica detalladamente tu razonamiento en la etiqueta de pensamiento.

<instrucciones>
1. Escribe todo tu proceso de análisis matemático dentro de la etiqueta <thinking>.
2. Escribe únicamente el veredicto final ("SÍ" o "NO") dentro de la etiqueta <resultado>.
</instrucciones>

<entrada>
El número a evaluar es: 7919
</entrada>
```

Claude procesará el prompt generando una respuesta estructurada como esta:

```xml
<thinking>
1. El número es 7919.
2. ¿Es par? No, termina en 9.
3. Suma de dígitos: 7 + 9 + 1 + 9 = 26 (no es divisible por 3).
4. Raíz cuadrada de 7919: aprox. 88.98. Debo probar divisores primos hasta 89.
5. Probando divisores:
   - 7919 / 7 = 1131.28
   - 7919 / 11 = 719.90
   - 7919 / 13 = 609.15
   - ... (pruebas intermedias) ...
   - 7919 / 89 = 88.97 (no divisible).
6. Ningún primo hasta 89 divide a 7919. Por lo tanto, es primo.
</thinking>
<resultado>SÍ</resultado>
```

## 5. Mitigación de Alucinaciones y Control de Formato

En entornos de producción, las alucinaciones (cuando el modelo inventa información) y las variaciones en el formato de salida son inaceptables. Afortunadamente, el taller de Anthropic ofrece técnicas claras para mitigar estos problemas.

### A. Dar una Vía de Escape (Evasión de Alucinaciones)

Si le pides a Claude que extraiga información de un documento y esta no existe, el modelo por defecto intentará complacerte extrapolando o inventando. La solución es darle permiso explícito para admitir que no sabe la respuesta.

```xml
<!-- ✅ Prompt defensivo con vía de escape -->
Analiza el contrato proporcionado y responde a la pregunta.
Si la respuesta no se menciona explícitamente en el texto, responde exactamente con "INFORMACIÓN NO DISPONIBLE".
No intentes asumir ni adivinar.
```

### B. Control Estricto de Formato (JSON / Raw)

Para integrar las respuestas de Claude en una API, necesitas un JSON válido sin texto introductorio (como _"Aquí tienes el JSON solicitado:"_). Puedes lograr esto combinando instrucciones específicas con un prefijo de salida.

```xml
Identifica las entidades (personas, organizaciones) mencionadas en el texto.

<instrucciones>
Devuelve los datos exclusivamente como un objeto JSON con la estructura: {"personas": [], "organizaciones": []}.
No incluyas explicaciones, saludos ni bloques de código markdown. Devuelve únicamente el JSON crudo.
</instrucciones>

<texto>
Alfonso Garcia fundó labitcode para explorar el desarrollo de software y la inteligencia artificial.
</texto>
```

## Resumen de Buenas Prácticas (Tu Checklist de Prompts)

Cuando construyas integraciones con Claude o cualquier LLM, usa este checklist para validar tus prompts:

- [ ] **Asigna un Rol**: ¿El prompt comienza definiendo el papel que debe adoptar el modelo?
- [ ] **Estructura con XML**: ¿Están los datos separados de las instrucciones mediante etiquetas legibles?
- [ ] **Proporciona Ejemplos**: ¿Has incluido al menos un ejemplo de entrada y salida esperada (Few-shot)?
- [ ] **Activa Chain of Thought**: ¿Le has pedido al modelo que razone paso a paso (`<thinking>`) antes de dar la respuesta?
- [ ] **Define Salidas de Escape**: ¿El modelo sabe qué responder si no encuentra la información solicitada?
- [ ] **Especifica el Formato**: ¿Has dejado claro si esperas JSON, Markdown o texto plano?
